Use a narrow `postgres/configuration_completion_store.py` (vended by the existing store bundle) and an internal issued `_PreparedConfigurationCompletion` bound to the actual stores/connection, L guard, owner request/run/attempt and candidate direct outcome. No new independently committing service, API endpoint, or caller-asserted completion method.

Separate pre-ID correlation/material preparation from binding the actual terminal event and outcome locator constructed by the fold. Use the existing prepared-then-bind pattern or equivalent exact owner validation before inserting the link; do not allocate speculative extra event IDs or bypass whole-result accounting. This parent design establishes topology, not that concrete per-child source ceiling.

## D2 target semantics and authority

Reservation occurs at **fresh cleanup attempt start**, not queue admission. Admission validates the exact C profile/subject/current approval and records intent only. Start rereads exact original plan/approval, current authority/fence, current occurrence, every relevant claim and D1 admitted completion under L, before IDs/writes. The original candidate/closure set must match byte-for-byte; no rescan expansion. It commits original intent/start plus immutable reservation/members/closures and claim dispositions, then returns the existing NewlyStarted permission. ExistingAttempt is observation only.

Proposed durable keys:

- Reservation header: cleanup Attempt PK, original request/plan/approval subject fingerprint and original effect/start identity, exact candidate count/digest and expected context.
- Reservation member: `(cleanup Attempt, workspace_id, allocation_id)` with a unique `(workspace_id, allocation_id)` exclusion, exact full-ref/root source and immutable header FK. It is the approved intent's resource set, not an allocation registry.
- Use closure: original ordinary Attempt PK, exact admitted completion FK, whole-selection fingerprint and exact approved reservation/plan/approval linkage. All selected uses close together, only under the fresh reservation owner.
- Existing claim gains a write-once typed closure locator, backed by the same original RefKey and allocation scope in immutable disposition/closure evidence. Original identity/material/scope remain unchanged and reciprocal ref/claim FKs remain. NULL is protective; only NULL → exact validated locator is allowed, with equality-only replay. No reopen/clear/free status flag. Add constrained original runtime/node coordinates only if required for partial indexes.
- Per-candidate result/retirement: keyed by original reservation member and exact original cleanup terminal outcome; REMOVED/ALREADY_ABSENT retire only that allocation incarnation. The complete original result remains in the outcome owner.

Partial indexes discover protective claims by exact allocation and workspace/runtime/node, avoiding scans over discharged lifetime history. The seed/birth remains separately point-proved even after closure; every selected ref still requires its reciprocal original claim. Reservations and retirement are checked independently even when no active claims remain. Hot reads rely on guarded admitted immutable facts plus relational constraints; current-schema verification checks retained dispositions without rewriting them. Invalid/missing requested provenance or disposition proof refuses.

Before takeover C still sees its unchanged nonempty whole retained set. D-aware fresh read/publication/approval additionally refuses reserved/retired allocations and absent admitted links, within the same shared ledger; v1 wire and historical replay meaning are preserved. There is no new zero-claim planning case because the minimum never discharges a claim through advancement.

Reuse existing full-result conservation. A cleanup fold retires each exact REMOVED/ALREADY_ABSENT allocation and retains exclusion for **every** UNKNOWN, RETAINED_IN_USE or REFUSED candidate. Header/members/closures remain immutable history. No result reopens claims, releases an unresolved reservation, or licenses a second dispatch. Explicit future resolution/retry is outside v1. Mixed outcomes preserve known retirement and unresolved neighbors in one transaction. Provider absence and attachment verification remain I177 obligations; CPK excludes only cooperating writers.
