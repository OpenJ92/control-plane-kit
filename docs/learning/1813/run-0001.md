### Objects, transformations and executable laws

`RuntimeManagement(gateway_node_id, management_ingress_id)` selects resources
already present in the complete submitted topology. A product/block's
`GatewayTransitDeclaration` advertises its exact transit socket and closed health
profile. Its own SDK control surface is a separate declaration. Core's
`management_ingress_for_health_read(validated_graph, node_id, socket, kind)`
requires the exact workload declaration and runtime-local relationship.
Server reception validates and preserves supplied gateway, connector and ingress
values. It does not insert infrastructure or require another authored packet.
UI/client convenience belongs before submission and grants no authority.

`compile_graph_activity_plan(current, desired)` derives its own graph diff using
the existing activity/dependency algebra. Distinct `ObserveManagementBootstrap`
stages request gateway-local readiness, connector connection and authenticated
management-path availability; `ObserveNodeHealth` requests an explicitly supported
workload kind through that runtime's gateway. Initial ordering is gateway start
→ local readiness → ingress allocation → connector start → connection observation
→ authenticated path → workload health. Retained connector reconciliation also
waits for gateway-local readiness. Real service edges remain intact, and a real
dependency cycle raises `InvalidActivityPlan` rather than producing success.

Observation targets pin runtime, graph side, graph digest and relationship digest.
`resolve_management_observation(candidate, current, desired,
expected_operation=operation_from_accepted_plan)` checks independent expected
operation material; callers must not derive that expectation from the candidate.
Semantic pins provide correlation, not current attempt admission or freshness.
These are requested observations and ordering laws. No connection observer,
authenticated-path transport, unavailable/unknown result producer or live health
outcome is implemented by this parent. Process liveness is not tunnel readiness.

Operations' closed `PlanDerivationProfile` and shared `derive_activity_plan`
preserve recorded compiler meaning. Legacy absent markers and explicit
`structural-v1` reproduce their historical plans. Fresh plans now select
`management-graph-pair-v1`; plan/action profile presence and values must agree
before reproduction. Existing request fingerprints, pinned history, result
congruence and rotation semantics survive. Old readers reject new envelopes or
operation kinds: readers must be upgraded before new writes, and downgrade
cannot silently reinterpret existing records. No historical row is rewritten.

Fresh `runtime_management_planning_is_unsupported(transition, *,
registered_products=())` parses every node reference before the canonical-empty
exception. For nonempty plans, matched registered management projections must
agree per node on both graph sides. Nodes carrying transit or SDK surfaces need
management selected in their own same-side runtime; plain nodes remain admissible.
A faithful sibling cannot hide another node's omitted declaration. Unselected
SDK base-to-selected repair remains refused. The extra pure canonical derivation
is a deliberate cost; unrelated product fields and catalog entries do not become
a general congruence audit.

Complete selected pairs may persist Core's ready or explanatory review plans.
Variable declarations grant no variable effects; unsupported readiness never
falls back to private HTTP. A fresh compiler cycle becomes a fixed,
cause/context-free `ActivityPlanningGraphInvalid` before plan/action/event/
observation writes. Replay uses stored policy without fresh admission. Direct
and coordinator execution still refuse management material, including ready
graph-pair plans, with zero effects and preserved exact denied receipts.
