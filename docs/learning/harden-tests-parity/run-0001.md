## #1330 Session command serialization contract

The #1321 operations reconciliation exposed two related transaction-order
defects: identical desired-graph commands could lose replay to stale-pointer
handling, and planning could publish after a concurrent close. A broader source
audit showed that the inconsistency spans every operation-action writer rather
than only those two services.

The accepted global order is now explicit:

```text
command identity advisory lock
  -> durable replay read
    -> session row FOR UPDATE and lifecycle re-read
      -> workspace row FOR UPDATE when required
        -> narrow dependent rows
          -> action ordinal while session remains locked
            -> domain writes plus action
              -> one application-owned commit
```

`start-operation-session` remains the pre-row exception and uses its existing
workspace/idempotency creation lock. Every other action writer has one closed
role map in `control-plane-kit-operations/session-command-serialization.json`.
The structural package tests reject missing writers, duplicate roles, role-order
inversions, and incomplete replay/terminal/transaction outcomes.

This contract intentionally serializes commands inside one session while
retaining concurrency across independent sessions. It does not introduce
process locks, retries, execution leases, or external-effect recovery. Those
remain separate from this Postgres transaction-order correction.

## #1331 Postgres session serialization primitives

The activity-history store now exposes exactly two implementation primitives
for the #1330 contract:

- `lock_action_idempotency(session_id, idempotency_key)` takes a namespaced
  transaction advisory lock before an action row exists;
- `get_session_for_update(session_id)` selects and returns the complete
  authoritative session lifecycle row under `FOR UPDATE`.

The advisory lock is command identity, not lifecycle authority. The session row
lock is lifecycle and action-order authority. Keeping those roles separate lets
identical commands converge before pointer validation while still serializing
distinct commands that mutate one session.

Real Postgres tests with independent connections proved that a duplicate
identity blocks, the same key in another session does not block, a later row
lock owner sees a committed terminal status, concurrent action writers allocate
unique monotonic ordinals, and rollback releases both lock types while removing
partial action evidence. `lock_timeout` supplies bounded blocking proof without
sleeps or process-local coordination.

The primitives do not commit, roll back, retry, or accept caller-selected lock
names. The application UnitOfWork remains the sole transaction owner.

## #1332 Desired graph replay convergence

`DesiredGraphCommandService` now acquires the session/action identity advisory
lock before reading replay evidence. A missing replay then leads to the exact
session row `FOR UPDATE`, workspace ownership and `OPEN` validation, and only
then the existing workspace compare-and-set and action append.

This order makes two superficially similar races intentionally different:

```text
same key + same intent
  -> wait for the first transaction
    -> replay its exact graph, projection, revision, and action

distinct keys + one expected pointer
  -> serialize on session lifecycle
    -> one command mutates the pointer
      -> the other reports truthful stale state
```

The previously failing #1321 concurrency test was copied unchanged and now
passes. Additional real Postgres evidence proves one desired graph version, one
realized projection, one workspace revision increment, and one action for the
identical race. Exact replay also survives a later desired pointer change and
session close because durable replay is resolved before current lifecycle or
pointer validation.

No retry loop was added, stale semantics were not weakened, and graph truth and
action evidence remain one UnitOfWork transaction.

## #1333 Planning and terminal-session fencing

Activity planning and close/cancel now share the same identity-first session
order. Planning resolves durable replay before state validation, locks and
re-reads the session, requires `OPEN`, and only then locks workspace graph truth.
Close and cancel resolve replay under their command identity, then lock the
session before terminal validation, ordinal allocation, transition, and action.

The resulting race has only two legal durable histories:

```text
request-activity-plan -> close-or-cancel

close-or-cancel
  -> planning observes terminal state
    -> no plan or planning action
```

The formerly observed `close-operation-session -> request-activity-plan` order
is impossible because planning cannot validate `OPEN` from an unlocked snapshot.
Exact plan and terminal replays remain available after terminal state because
committed evidence is read before current lifecycle validation.

Directed real Postgres tests use injected clocks as transaction barriers and a
connection observer to prove the actual session `FOR UPDATE` statement was
attempted or acquired. They do not use sleeps, process-local production locks,
or service test hooks. Bounded futures prove planning-before-terminal,
terminal-before-planning for both close and cancel, identical plan convergence,
write-once terminal state, and absence of deadlock in these lock orders.

## #1360 Exact current-backend source lock

unknown/duplicate distributions, malformed coordinate manifests, unsafe paths,
duplicate archive members, and extraction collisions. This gives #1361 exact
source trees and bounded coordinate evidence without switching, stashing,
resetting, or cleaning any developer checkout.
