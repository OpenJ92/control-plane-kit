# HARDEN.DATA Operations Schema Baseline Reset

## Outcome

CPK operations now owns one direct current Postgres schema and no schema
upgrade language. Installation has three observable outcomes:

```text
object-free owned namespace -> create and verify current schema
exact current namespace     -> verify without mutation
anything else               -> bounded reset-required failure
```

The schema contains 29 functional relations and 94 contract indexes. The
production read-cardinality inventory contains exactly 46 `fetchall()`
selector sites: 14
public-paged, 1 fixed-cardinality, 2 closed-finite, 22 internal-complete, and 7
exact verifiers. There is no version registry, durable installation ledger,
compatibility interpreter, repair path, or backfill authority.

## Why This Shape

The package is not in external use, and historical internal database layouts
have no product value. Keeping a long compatibility program made installation,
tests, review, and lock behavior materially harder without protecting a live
consumer. The reset therefore removed that machinery from production, tests,
fixtures, exports, and documentation instead of preserving a smaller facade.

The exact current contract remains independently represented because stores
need stable table, column, constraint, and index truth. It is verification
data, not an upgrade plan.

The direct SQL started from `pg_dump (PostgreSQL) 16.14` against a disposable
database installed at the accepted pre-reset coordinate:

```text
pg_dump --schema-only --no-owner --no-privileges --schema=<disposable-schema>
```

The checked-in artifact was then reviewed and reduced to schema-local
`CREATE TABLE`, `CREATE [UNIQUE] INDEX`, and `ALTER TABLE ... ADD CONSTRAINT`
statements. Owner, ACL, session, search-path, extension, schema-creation,
comment, and environment output is absent. No dump tool or generator is a
production dependency.

## Executable Laws

- installation mutates only an object-free owned namespace;
- the checked-in SQL contains only current table, index, and constraint
  assembly and has deterministic package bytes;
- current reinstall performs bounded reads and relation locks only;
- current reinstall preserves rows and object identities;
- drift and unrelated owned objects are rejected without repair or row loss;
- cross-schema objects are ignored and preserved;
- fresh-install failure rolls back every schema effect;
- concurrent fresh installers serialize on one schema-scoped advisory lock;
- caller-owned outer transactions retain commit and rollback authority;
- failures are categorical, bounded, cause-free, and redact driver details;
- all functional store and workflow tests run against the direct baseline.

## Data And Operational Boundary

CPK does not reset a database. The installer only reports that reset is
required. Any valuable operational data must be inventoried and preserved by a
separately reviewed operator procedure before an owned namespace is removed.
No existing database or Docker volume was inspected or reset during this
change; validation used disposable issue-scoped PostgreSQL instances.

The transaction-scoped advisory lock serializes installers. Verification holds
a fixed SHARE lock on each current relation until the enclosing transaction or
savepoint ends. PostgreSQL and the caller own wait policy and any outer
transaction lifetime.

## Future Schema Changes

A future change edits the one current schema and exact semantic contract. It
must include fresh-install, current-verification, rollback, lock, redaction,
store, and operator reset-consequence tests. It must not restore version,
ledger, suffix planning, compatibility, or inferred repair behavior without a
new and independently justified product requirement.
