# HARDEN.DATA.1 Exact Schema Convergence

## Outcome

DATA.1 replaced implicit schema repair with an explicit, checksummed migration
language. PostgreSQL installation now follows one path:

```text
inspect durable schema and ledger truth
  -> select an immutable V1-V17 migration suffix
    -> acquire the declared advisory and relation locks
      -> execute ordered SQL and deterministic backfill steps
        -> record exact migration identities
          -> verify the exact current contract
```

An already-current schema takes the empty suffix. It acquires the current-schema
lock plan and performs bounded verification only; it does not submit DDL or a
durable mutation.

## Objects And Transformations

- `SchemaMigration`, `SqlMigrationStep`, and `DeterministicBackfillStep` are the
  immutable migration language.
- `SchemaMigrationRegistry.plan(observed)` selects the only accepted suffix.
- `ObservedPostgresSchema` separates empty, exact unversioned V1, and versioned
  durable truth.
- `install_postgres_schema(connection)` interprets the selected suffix inside a
  caller-aware transaction.
- the current-schema contract interprets bounded catalog observations into five
  exact structural booleans; ledger and migration-local verifiers remain
  separate bounded observations.

## Executable Laws

- frozen V1 bytes and checksum remain unchanged;
- no-ledger adoption accepts only the exact ordered V1 manifest;
- ledger entries are contiguous, named, and checksummed V1-V17 identities;
- all canonical and six historical append-order fixtures converge through the
  same immutable migration programs;
- current column order is irrelevant when exact column semantics agree;
- unknown tables, columns, constraints, indexes, types, defaults, precision, or
  ledger truth are rejected rather than repaired;
- already-current reinstall preserves rows, relation/constraint/index
  identities and definitions, and ledger `applied_at` values without mutation;
- failed SQL, backfill, ledger recording, or final verification rolls back the
  runner-owned transaction or nested savepoint;
- advisory and relation lock behavior remains bounded and caller-aware.

## Transaction And Concurrency Truth

With an autocommit connection, the runner owns the top-level transaction. With
an existing caller transaction, the runner owns only a nested savepoint; the
caller retains commit/rollback authority and the lifetime of outer locks.
Concurrent installers serialize on the schema-scoped advisory lock. The
advisory key and relation lock set are fixed and bounded; wait duration and the
lifetime of caller-owned outer-transaction locks remain controlled by
PostgreSQL and the caller. A failed nested migration releases savepoint-owned
locks without discarding unrelated caller work.

## Review Learning

The original convergence path rendered a second mutable copy of the schema and
executed it after migration selection. That made migrations appear complete
while retaining an unplanned repair interpreter. DATA.1 first made historical
changes explicit, then added exact semantic verification, and only then retired
the replay. This order exposed missing migration behavior without risking live
schema mutation as a discovery mechanism.

Physical column order was also an accidental historical classifier. Exact
catalog semantics now accept arbitrary order for versioned current schemas,
while exact ordered V1 remains necessary for safe no-ledger adoption.

The pre-V17 graph-lineage constraint fixture is test-owned and pinned. The
production V17 constraint inventory remains because it constructs and verifies
the immutable V17 migration; tests no longer use that private production value
as their source of historical truth.

## Security And Data Posture

No route, authentication, secret, or external network surface was added. The
work reduces mutation authority: drift cannot trigger opportunistic repair.
Migration and verification failures remain categorical and do not retain
provider exceptions, query text, addresses, credentials, or row payloads.

CPK owns its operations schema, migration ledger, and durable operational data.
It does not own or migrate client-application schemas or data, or decide client
rollout readiness. Client applications remain responsible for their own
compatibility and data-migration procedures before CPK is asked to evaluate
deployment completeness.

## Deviations And Residual Risk

The migration series became longer than initially expected because frozen V1
contained several generations of compatibility behavior. No compatibility SQL
was silently rewritten: each retained change received an immutable migration
owner before replay retirement.

Residual risks belong to later roadmap nodes:

- PostgreSQL backup/restore, downgrade, and full historical readiness acceptance
  remain under #1112;
- bounded operational reads, cursors, and any query-index successor migrations
  remain under #1111;
- reclaim, fencing, and migrations required by those behaviors remain under
  #1105;
- application-specific data migration and compatibility remain outside CPK.

## Handoff

Future schema changes must append a new immutable migration value with preflight,
execution, verification, rollback, concurrency, and redaction laws. They must
not reintroduce a rendered current-schema replay or infer repair authority from
physical column order.
