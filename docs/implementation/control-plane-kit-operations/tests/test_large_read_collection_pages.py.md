Six real-Postgres test methods exercise collection-store paging over synthetic 201-row datasets and selected changes between reads. They own storage selection/order/cardinality, not HTTP/MCP transport, operator approval, provider reality, redaction of public responses or deployment lifecycle correctness. Use the established Docker-backed package suite for execution; no new execution accompanied this note.

Each seeded context requires the configured test database URL, creates a UUID schema on an autocommit connection, sets search_path and installs schema. A finally block attempts RESET, exact-schema DROP CASCADE and connection close sequentially; failure of an earlier cleanup call can prevent later calls. The URL itself is trusted rather than proven disposable. Most changes commit statement-by-statement; catalogue construction and deliberate uniqueness failures use explicit transaction contexts.

The traversal test covers 18 collections with limit 100 and exact page sizes 100/100/1, compares the full identity sequence, rejects duplicates, checks both continuations and final exhaustion, then seeks after the independently constructed final cursor and expects an empty page. Two max 10 revision preparation/attempt histories remain explicitly owned by test_revision_history_pages; the two sets must cover all twenty collection enums. This is finite dataset evidence, not arbitrary-scale performance, bounded database work or a stable snapshot.

Temporal cases insert values on both sides of an old cursor, close an open session, attach approval decisions, remove a pending approval and change a run status. Continued pages respect the strict position while fresh reads expose earlier inserts/current values. In particular, an already-before-cursor run is absent from continuation because of position, not because its failed status is filtered. Decisions on session approvals change joined data without removing the request; decided pending approvals leave that filtered view.

Ordinal cases append action/event 202 after page 1 and traverse the remainder. Separate duplicate-ordinal inserts must raise actual PostgreSQL UniqueViolation, roll back inside the explicit transaction, leave no candidate residue and permit a subsequent ordinary read. They do not exercise two simultaneous writers or allocator locking. The remainder helper loops until next_cursor=None without its own iteration/deadline bound.

Current-identity cases replace an observation and re-register runtime, delivery, ingress or provider metadata behind a cursor. Continued pages do not revisit that identity, but fresh pages return the replacement registration. Reference revocation/insertion and observation insertion test current membership on each statement. Some changes use actual stores, others direct fixture SQL; none prove the corresponding public commands or authority admission. Remote TLS and Cloudflare values are synthetic handles, with no network/secret resolution. Delegation retirement changes returned status without removing the full purpose/issuer/key tuple from a fresh page. Probe head/tail insertion checks descending issued_at/probe_id continuation: a newer head requires fresh traversal while an older tail remains reachable.

Shared seeds directly insert empty plans, approvals, cancelled execution requests, succeeded runs and repeated run_started events. These deliberately shaped rows satisfy read fixtures rather than establish a coherent executed history. The catalogue helper creates empty graph records and draft revisions under a workspace lock; it does not deploy graphs. Selected schema/row behavior must not be promoted into provider success or recovery claims.
