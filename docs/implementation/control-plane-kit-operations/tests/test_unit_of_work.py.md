Eight methods exercise [PostgresUnitOfWork](../src/control_plane_kit_operations/postgres/unit_of_work.py.md): five fake-connection lifecycle tests and three PostgreSQL integration tests. They own the caller transaction boundary, not command authorization, domain idempotency or provider outcomes. No tests were run for this note; executable validation belongs to the established Docker-backed Operations suite.

FakeConnection counts physical commits, rollbacks and closes. Its execute method raises immediately, ensuring these lifecycle cases do not execute SQL. The happy path requires the bundle's connection to be the supplied object, no bundle-level commit/rollback attributes, zero physical commits immediately after requesting commit, and one commit/one close on exit. The same bundle remains accessible after the request. That is delayed commit behavior, not a security boundary preventing use of the exposed connection.

Other fake cases cover unrequested exit, an application ValueError, an exception after requesting commit and a physical commit OSError. They require the selected commit/rollback/close counts and expected exception text/type. The state test checks store access before entry, a duplicate commit request and rollback after completion. It does not exhaust lifecycle transitions, retained store handles, reuse after close, nested entry, manual close inside a context, connection-factory/bundle failures, rollback/close failures or cancellation. Fake rollback succeeds by construction; commit-failure counters do not establish what a real database durably committed.

Integration setup trusts CPK_OPERATIONS_TEST_DATABASE_URL, connects with an autocommit observer, installs schema and TRUNCATEs cpk_workspaces CASCADE. It does not create a unique schema or independently validate a disposable target. Each UoW opens a separate transactional connection; tearDown closes the observer, with no independently guarded setup-failure cleanup. Package harness ownership/isolation is a prerequisite, not provided by this file.

The commit-visibility test performs one workspace INSERT through the shared connection and observes zero rows both before and after requesting commit, then one after context exit. Despite its broad name, it does not exercise writes across every domain store/table. The late-write test attempts a duplicate primary identity, expects actual UniqueViolation and sees zero workspace rows afterward. The final case requests commit, raises an application RuntimeError and also expects zero rows. The count helper allows only cpk_workspaces. These are finite transaction/visibility examples, not concurrent readers/writers, connection loss, process crash, serialization retries or all-schema atomicity tests.

Read depth: full 182-line tests/fake, full 102-line UoW and full 248-line store-bundle composition. The note describes assertions rather than a new green result. No production/test edits, SQL execution, provider actions, credentials or new validation machinery were introduced.
