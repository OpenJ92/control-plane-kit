These four Operations tests exercise stored revision-history pagination with real Postgres queries through RevisionHistoryFixture. The inherited catalogue fixture requires CPK_OPERATIONS_TEST_DATABASE_URL and trusts that configured URL; it does not independently verify the database's origin. It creates a uniquely named disposable schema, installs the current schema and registers schema cleanup. The established Operations test.sh supplies the disposable Docker database and owns launcher isolation. Use only that suite for executable validation; these tests call no provider, and no execution was performed for this companion.

The tests protect four concrete boundaries:

- A directly inserted oversized session identity in the hidden lookahead candidate fails the whole preparations page, even with limit one. The error is bounded and does not echo that identity; the selected eight-table history snapshot is unchanged. Direct SQL deliberately bypasses typed record admission to represent malformed retained data.
- Each collection traverses 201 tied-time rows in ascending identity order, with page sizes twenty tens plus one, no duplicates, and revision-scoped cursors. A later empty page does not erase complete-relation presence. The first-page descriptors agree across direct store, InstanceReadService and HTTP/MCP-labelled CpkServerReadService requests without changing the selected history tables.
- Commits after a page affect later traversal according to the cursor position: newly inserted earlier items require a fresh traversal, while later ones appear on continuation. Both attempt identity ties and preparation chronology are exercised. This deliberately makes no cross-page snapshot claim.
- A representative 32-session, three-attempt-per-plan fanout captures real SQL through a forwarding connection wrapper. Limits one and ten have equal query counts, at most two statements including parent admission. EXPLAIN ANALYZE records top-node output rows and execution time; top output is at most eleven. There is no latency threshold or proof that internal scan work is bounded independently of database size.

Fixture records establish historical relationships, not actual effect execution. add_attempt writes typed approvals, requests and runs directly, and explicitly claims no execution or advancement; a stored run status is not provider acceptance. The protocol-labelled read calls exercise Operations adapters using fixture principals, not a running HTTP server, real MCP transport, token verification or external authorization infrastructure. The unchanged-table checks are selected history checks, not an exhaustive database/provider audit.
