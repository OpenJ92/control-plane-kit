Six methods compose the actual cpk_server_services factory, preparation program and read service with real package stores. The inherited saved/draft fixture creates a unique schema inside the trusted Operations-suite database; units of work use its search path and cleanup drops that schema. Requests are CatalogueRequest values labeled http or mcp, with an already constructed trusted principal. These prove Operations request composition, not network transport, token verification or a running server/provider.

The first method prepares through HTTP-shaped input and replays the same command through MCP-shaped input, comparing response and selected durable tables. Forged actor/scopes in payload must not control the result. A ten-case matrix checks mutually exclusive inline/saved input, missing saved coordinates, selected scalar bounds and stale generation with matching 400/409 text on both surfaces, selected canary suppression and no compared-table changes. These checks are not a blanket closed-field parser or an exhaustive descriptor validator.

Authorization uses a fail-on-access program/UoW to reject missing principal, foreign workspace and each insufficient-scope combination before command/store entry on both surfaces. The class still inherits database setup, even for this early-denial test. It tests authorization of a supplied principal, not how HTTP/MCP authenticates credentials.

Overview tests distinguish the historically prepared revision from a later draft head, preserve the selected plan, expose pending approval rather than execution and keep run-history/cursor empty. Wrong/missing relational source and partial/false/extra saved commitment fields produce unavailable prepared provenance. Selected snapshots verify no repair. Complete erasure of both source and saved-origin evidence explicitly becomes none, not a guessed historical origin. Direct SQL corruption is fixture setup for these laws, not a supported repair path.
