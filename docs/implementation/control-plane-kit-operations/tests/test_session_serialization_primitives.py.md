Five real-Postgres tests exercise session action-identity locks, session row locks, ordinal allocation and UoW rollback. Unlike the [serialization contract tests](test_session_command_serialization_contract.py.md), these tests interact with the database primitives. They still do not prove every command's lock order, authorization, replay or external-effect behavior. No tests were executed for this note; use the established Docker-backed Operations suite when authorized.

Setup requires CPK_OPERATIONS_TEST_DATABASE_URL, opens an autocommit administrative connection, installs schema and TRUNCATEs cpk_workspaces CASCADE. It creates two workspaces and two OPEN sessions with ordinal-1 start actions through stores, not public command admission. There is no UUID schema or independent disposable-target check. Each worker/UoW uses a new transactional connection. tearDown closes the administrative connection; it does not remove all seeded rows, and setup failure before tearDown is not independently guarded here. The package harness owns database isolation and resource lifecycle.

The first test takes the same session/action identity lock on two connections. The second connection has a 250 ms transaction-local lock timeout and must raise LockNotAvailable while the first transaction holds the lock. After both roll back, the second acquisition succeeds. This exercises rollback release, not a commit-release variant or fingerprint conflict. The independent-session test takes the same key for the two different sessions/workspaces and requires the second acquisition to succeed under that timeout. It is a selected independence example, not proof that every advisory-key encoding/hash is collision-free or every workspace relationship is covered.

The row-lock test reads OPEN with get_session_for_update, requires a competing lock to time out, rolls back the second transaction, changes the first row to CLOSED and commits, then requires the second locked read to see CLOSED. The [actual store](../../../../control-plane-kit-operations/src/control_plane_kit_operations/postgres/activity_history.py) uses SELECT FOR UPDATE and an OPEN-conditional transition. The test observes serialized terminal truth but does not invoke a nonterminal command afterward to prove its admission denial. The post-rollback reads do not retain the earlier SET LOCAL timeout.

Two worker threads start behind a five-second barrier, each with a different command key for session-a. Each locks identity then session, allocates the next action ordinal, inserts one synthetic action and requests commit. Results must be {2,3}; the administrative read requires the original ordinal-1 action and exactly the two new identities/ordinals, without selecting a winner. The allocator itself re-locks the parent before MAX(ordinal)+1. This is a two-writer success case, not same-key replay, arbitrary contention, failure recovery or a repeated stress test. Each future result has a ten-second timeout, but database statements and executor-context shutdown do not have a universal bound; the context can wait for workers even after a future timeout.

The rollback test inserts an action but deliberately never requests UoW commit. A fresh UoW must reacquire the same identity/session locks, find no action under that key and allocate ordinal 2 again. [PostgresUnitOfWork](../../../../control-plane-kit-operations/src/control_plane_kit_operations/postgres/unit_of_work.py) commits only on successful context exit with commit requested; otherwise it rolls back and closes. The second verification UoW also exits without commit. This test covers implicit rollback of the selected partial action, not commit failure, process loss, exception normalization or every table's transaction behavior.

Explicit-connection tests attempt rollback/close sequentially in finally blocks; an earlier cleanup exception can prevent subsequent calls. They are not a cleanup-fault suite. Seeded actor IDs, action kinds and fingerprint strings provide relational prerequisites, not authorization, generated intent hashing or durable executed workflow evidence. No provider, credential, graph mutation or public HTTP/MCP path is exercised.
