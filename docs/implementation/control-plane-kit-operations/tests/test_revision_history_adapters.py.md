Three tests prove the Operations read-adapter boundary for both revision-history collections. They call CpkServerReadService directly using CatalogueRequest and fixture principals; HTTP/MCP are request representations, not running protocol servers or token-verifier tests.

The first test gives the service a UnitOfWork factory that fails if called. An absent principal or a principal granted only another workspace must receive 403 before malformed cursor/limit processing or any store access, across both surfaces and collections. The malformed input canary must not appear in the error. The second uses the same fail-on-UoW shape for authorized HTTP requests: over-limit/bool limit, empty cursor, extra argument and revision zero produce 400 before opening storage. That second negative matrix is HTTP-only; it should not be described as exhaustive cross-protocol malformed-input parity.

The third prepares real stored draft/plan/attempt fixtures and compares direct page descriptors with both adapter representations, including the default limit ten. An authorized request for the draft in another workspace, or a missing revision in its own workspace, returns 404. These are non-disclosing read outcomes, not proof that a caller's missing credentials are cryptographically rejected by a deployed server.

Full owner read with [shared fixture](./revision_history_fixture.py.md), selected inherited request/principal construction and the actual [CpkServerReadService authorization/closed-page dispatch](../../../../control-plane-kit-operations/src/control_plane_kit_operations/cpk_server.py), plus the reviewed [read projection](../src/control_plane_kit_operations/read_services/revision_history.py.md). Even the fail-on-UoW cases inherit database-backed fixture setup. Execute only through the established Docker Operations suite; no execution was performed here. These tests do not authorize provider access or introduce durable command semantics in adapters.
