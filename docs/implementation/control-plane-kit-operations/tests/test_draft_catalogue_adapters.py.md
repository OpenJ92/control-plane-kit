These five methods test create/revise and three catalogue read routes at the Operations adapter boundary. [DraftCatalogueFixture](draft_catalogue_fixture.py.md) supplies actual schema-local PostgreSQL, command/read services, synthetic product graphs and a typed principal. CatalogueRequest moves coordinates into HTTP-like paths or MCP arguments; direct handle calls prove mapping/parity, not real server transport or authentication. The suite must run only through the established Operations Docker-backed harness.

The first method uses cpk_server_services rather than just a manually built planning adapter. Create/revise through both shapes return matching workspace/draft/revision/graph coordinates, with the later call replaying the same intent. Summary, revision-page and detail responses match across shapes. All operation actors remain the trusted operator despite a forged actor/scopes payload, and selected runtime tables remain unchanged. This is durable catalogue intent, not provider execution or topology convergence.

Missing, foreign-workspace and insufficient-scope principals cannot reach ForbiddenCommands or the read UoW for either command or any of the three reads. Fixture database initialization already happened; “before store access” refers to the denied request. The command uses trusted context established outside payload authority, while these tests do not exercise a credential-verification layer.

Malformed graph and stale-head cases compare fixed bounded error descriptors across both surfaces and preserve selected catalogue tables. Overlong idempotency keys similarly produce 400 without echoing the supplied marker or writing catalogue state. Revision-detail requests with overlong draft IDs are rejected before opening the read transaction. These are concrete local error/redaction checks, not blanket sanitization of stored graph metadata, driver errors or every possible input.
