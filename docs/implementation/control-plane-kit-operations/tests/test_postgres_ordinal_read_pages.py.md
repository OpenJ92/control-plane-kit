Eight methods cover session-action and run-event ordinal paging: four recording-SQL tests and four real-Postgres/read-projection tests. They do not run a deployment coordinator, contact a provider or demonstrate a valid executed activity sequence. Validation remains the established Docker-backed Operations suite; this note records source review, not a new test run.

Recording connections return supplied rows and capture SQL/parameters. First-page tests assert no tuple seek, ascending ordinal/ID order and parent plus limit+1 parameters. Continuation cases assert exclusive tuple seek and verify that the exposed row, not hidden lookahead row, supplies next_cursor. These tests exercise actual row decoding/page construction against fake rows, not PostgreSQL parsing, index choice, query cost or concurrent ordinal allocation. Store SQL is scoped by session/run ID; workspace containment is a read-service responsibility, not independently applied by these selectors.

The database fixture requires CPK_OPERATIONS_TEST_DATABASE_URL, opens an autocommit connection, installs schema and TRUNCATEs cpk_workspaces CASCADE before seeding. It does not create a unique schema or discover whether the URL is disposable. The normal package harness owns isolated Docker setup; the fixture closes its connection in tearDown. Running it against unrelated data is not authorized by its test name or this documentation.

The seed inserts workspace/session, real graph versions and identity projections through the shared helper, then directly inserts an empty plan, approval request/decision, queued execution request and claimed run. Three actions and three events are added through their stores. The approval/execution rows are fixture truth rather than evidence that approval/admission/worker commands ran; repeated RUN_STARTED events are pagination data, not a coherent live event history. Graph identity construction likewise establishes local lineage, not provider realization.

Two append tests read/commit page 1, append ordinal 4 in a separate writer UoW, then read/commit page 2 in another UoW. They observe [1,2] followed by [3,4], last-visible cursor 2 and terminal next_cursor=None. They show visibility across sequential committed transactions, not simultaneous writers, a stable snapshot, exactly-once execution or process restart. The test uses the next-ordinal helpers without a competing writer, so it does not establish race safety.

The projection case checks exact page envelope keys, one api_token redaction canary, preserved event note, and a thin session summary without embedded actions/plans/approvals. It does not exhaustively certify secret handling or payload schemas. Three containment negatives replace selected run/request getters: missing run, missing request and foreign request workspace each produce the same missing-run-in-workspace ReadModelError before event_page is called. This is a concrete read-service non-disclosure boundary, not HTTP/MCP authentication or full malicious-store coverage.
