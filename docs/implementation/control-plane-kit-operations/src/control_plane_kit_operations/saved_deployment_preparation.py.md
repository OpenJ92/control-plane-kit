This owner admits an exact saved draft revision and binds it to an existing Operations session/action transaction. It does not select the desired graph, create a plan/approval, approve or execute effects. DeploymentProgram calls it for SavedDesiredTopologyRevision, then separately invokes existing planning and approval-request services. Admission can therefore be durable before a later preparation stage finishes; there is no transaction spanning the whole program or provider work.

Saved metadata has a closed saved-revision.v1 shape, bounded string coordinates, canonical positive revision/generation strings and a lowercase SHA-256 intent commitment. The commitment covers requested workspace/actor, draft revision, expected current/desired lineage, title and approval comment; the comment itself is not copied into metadata. A separate StartOperationSession fingerprint binds actor/title/metadata. These hashes detect inconsistency against retained command evidence; they are not signatures, secret redaction or proof against an actor able to rewrite all related facts. Legacy metadata without any saved-origin marker remains distinguishable from malformed partial saved evidence, not from complete erasure.

start requires exact preparation/saved-input types and both workspace-edit and plan-request scopes from the supplied command context. It does not authenticate credentials. The parent derives a stage-specific session key from workspace and parent idempotency key; this service serializes that key before lookup. Existing admission compares metadata, delegates session/action replay to start_in_unit_of_work, validates immutable graph/projection and saved source/revision evidence, then returns the retained result. Replay skips fresh current-pointer, draft-existence/tombstone and product-active admission checks; it also does not blindly accept missing retained provenance. First admission accepts the exact selected immutable revision without requiring it to be the latest draft head.

First admission takes key, workspace and draft locks before inserts. It requires a live matching draft and exact current/desired graph-projection/generation expectations, then validates the selected revision and referenced graphs. Desired projection must equal the identity projection for its authored graph. Current projection must belong to the current authored graph/workspace and both descriptors validate; it need not be an identity projection. Referenced products must be recorded active. The service starts the session and first action through the existing command owner, verifies their matching actor/key/fingerprint/time and inserts the four-field saved-source association. Those writes share one unit of work and commit/rollback together. This is not a lock or health check over external providers.

The exported metadata/session/source helpers support historical reads and current-data verification without replaying commands. Source validation checks the session commitment and revision identity/graph agreement; start-evidence validation separately checks ordinal-one START_OPERATION_SESSION evidence. Neither helper substitutes for every other admission fence or proves subsequent execution. The [source store](./postgres/saved_preparation_source_store.py.md) owns relational insertion/lookup, not these workflow semantics.

Inside the transaction wrapper, expected key/value/type/attribute/operation-command failures become fixed SavedPreparationError after leaving the handler, without raw cause/context. Input-type, scope and metadata construction happen before that wrapper and have their own boundaries; unexpected exception classes and BaseException are not universally normalized. The parent converts SavedPreparationError to its fixed public program conflict. Do not log internal command metadata or arbitrary exception values as if a complete content scrubber had run.
