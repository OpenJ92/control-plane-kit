This projection assembles a bounded operator overview from recorded workspace, graph, plan, approval, run, receipt and event truth. A next_action is a suggested public operation with coordinates and required scope names, not an authorization decision or executable plan. This owner does not approve, claim, execute, advance graphs, inspect providers or commit a transaction. The caller supplies authorized stores and transaction context; the facade composes it.

Current/desired graph pointers require paired graph/projection IDs and graph ownership congruent with the workspace. Their relation compares stored lineage: converged is recorded equality, not a fresh health or provider-convergence observation. The projection does not load the realized projection itself. Desired-draft navigation separately reports the selected revision and present head; saved-preparation provenance validates its source/session/revision/plan joins. Missing or malformed draft evidence becomes unavailable rather than an invented draft selection.

Workflow selection admits one open-session, planned plan matching current base and desired graph/projection/revision. Two eligible plans or pending approvals are ambiguous, not resolved by sort order. Approval subjects, session and required destructive/non-destructive scope must agree. Run selection requires at most 100 records for one execution request, unique identities and a complete contiguous retry lineage with one leaf; gaps, overflow or competing leaves cannot become a convenient latest run. These are durable-record joins, not a recovery policy.

Command receipts must refer to that run, plan, admission and retry identity. The Postgres reader prioritizes unresolved admissions; otherwise it returns the newest two completions. One incomplete receipt stays incomplete, multiple incomplete receipts ambiguous. Completion chronology selects the latest unique result; tied times remain ambiguous and idempotency-key ordering does not establish currency. The overview summarizes a receipt; it does not replay commands or infer a completed result from empty event history.

History uses a workspace/run-bound page, default 50 and exact-integer limit 1..100. It checks page identity, run identity and unique sorted ordinal/event-ID pairs, then uses the existing event descriptor/redactor. This is a bounded page, not proof of complete or contiguous lifetime history. A supplied cursor without a selected run is rejected; selected-run cursor scope is checked by ReadPageRequest. Sensitive payload keys are redacted, not arbitrary string contents. Public coordinates and event structural fields remain producer-owned values.

The offered operation is intentionally limited: prepare when diverged with no plan; approval.decide for one pending approval; run.start for a claimed run; deployment.execute for a running run; graph.advance-current only for a succeeded run with a completed coordinator result. Ambiguity, unavailable history, incomplete/ambiguous receipts, attention-required coordinator results and failed/cancelled/compensation run states suppress progress suggestions. An absent offer does not prove that no other authorized product action exists; this is not the complete command state machine.

Repeated reads compare selected workspace, draft, plan/session, approvals, runs, request and receipt anchors. They detect observed changes but do not establish a globally atomic snapshot or protect a later command from races; command owners must revalidate. Expected KeyError/ValueError/TypeError/AttributeError paths reaching the outer fallback replace workflow/history/action with fixed unavailable shapes, dropping partly selected workflow coordinates. Previously validated graph pointers may remain visible. Input-limit errors, selected-run page-request scope errors and ReadPageError reaching the outer handler propagate. Within _read_history, however, event_page/validation/descriptor errors caught as ValueError (including ReadPageError) become unavailable history; other helper-local catches can also normalize errors before the outer handler sees them. Unexpected exception classes and cancellation are not universally swallowed. No raw store exception text is copied into the overview.
