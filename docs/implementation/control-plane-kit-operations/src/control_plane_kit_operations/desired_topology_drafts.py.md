This owner defines durable desired-topology catalogue records and four commands: create, revise, select and delete. Create/revise retain independent authored graph versions; they do not select a workspace pointer. Select installs an identity realized projection as desired intent and increments the desired generation; it does not establish provider realization. Delete tombstones the catalogue header, retaining revisions/graphs/history. None of these commands plans, approves, executes, inspects or removes provider resources.

Record/result constructors require bounded nonblank strings without Unicode control-category characters, exact positive bigint-range revision integers and canonical UTC times; tombstone actor/time must be paired. Command dataclasses defer their validation to the service. The service requires supplied TrustedCommandContext with workspace-edit scope, not credentials or network authentication. Create/revise encode the graph and bound its JSON transport to 1 MiB before entering the unit of work; semantic Core validation and workspace-active product checks are separate fresh-admission conditions. Encodability alone is insufficient.

Each command fingerprints normalized intent and locks the session/idempotency-key pair before action lookup. Existing matching actions resolve before new identity/clock allocation and fresh session-open, product-active, current-head or pointer admission. Create/revise replay checks the closed coordinate payload against the retained revision, graph descriptor, actor and creation times. Select replay checks its retained revision, expected resulting generation and exact identity projection; delete replay checks the retained tombstone against action actor/time. Changed intent or incongruent evidence conflicts. Replay returns historical command truth, does not reset the current desired pointer, and is not authority to execute that historical graph.

Fresh create/revise holds session then workspace and, for revision, draft locks. Revision requires a live draft at the expected head. New graph, draft/header update, revision and bounded coordinate action share one commit; an action failure rolls the earlier writes back. Fresh select/delete uses the same order. Selection compares the complete expected desired graph/projection/generation tuple and may select an older immutable revision, not necessarily the draft head. It revalidates graph/products and identity projection before saving the desired reference. Delete requires the expected live head and rejects any draft revision referenced by current/desired workspace graphs or either side of any activity plan, irrespective of plan status. The [store](./postgres/desired_topology_draft_store.py.md) performs this relational reference check under caller locks, not provider discovery.

Actions retain coordinates rather than graph bodies or submitted titles. Graph descriptors and draft titles remain durable input; these constructors are not general secret scrubbers. Public read redaction belongs to the [draft projection](./read_services/desired_topology_drafts.py.md). Named expected failures use fixed messages, often `raise ... from None` inside a handler: this suppresses displayed chaining, not every internal exception context. Unexpected database/runtime exceptions are not universally sanitized here. Fingerprints are consistency checks, not signatures against arbitrary coordinated database rewriting.

Full 489-line owner and full store read; selected actual catalogue schema/FKs, existing activity idempotency/UoW contracts and previously reviewed saved-preparation/identity-projection consumers checked. The [catalogue tests](../../tests/test_desired_topology_drafts.py.md) cover creation/revision/read/schema behavior; separate selection tests own additional reference-command cases. No execution or whole-package/dependency audit; documentation grants no database, runtime or cleanup authority.
