This pure Operations language binds each read collection to an exact scope class, cursor class, route identifier, keyset position and page-size profile. It does not authenticate callers, query storage, authorize reads or observe providers. The current twenty-entry table is descriptive routing/paging truth, not evidence that every producer or transport is correct.

Workspace, session, plan, run, draft and revision scopes validate their identifiers. General identifiers are exact nonempty strings of at most512 characters without Unicode category-C characters; whitespace-only strings are not separately rejected here. Run scope delegates canonical identity admission to Core RunId. Revision is an exact positive signed-int8 value. Collection/scope/cursor profiles use exact classes; wire mappings require ordinary dicts, exact keys, exact version1 integer and literal collection values, not arbitrary Mapping objects or coercion.

Ordinal positions require exact positive integers, with no int8 upper bound in this constructor. Temporal positions require valid six-fraction-digit UTC-Z text; epoch positions are exact integers in0..int8-max, serialized as canonical decimal strings without signs or leading zeros. Delegation positions combine a Core purpose enum with restricted lowercase issuer/key identifiers. These are transparent structured cursors, not signed capabilities, opaque secrets or authorization tokens. Scope equality prevents accidental cross-scope cursor substitution but does not authorize access to that scope.

Most profiles default to50 and cap at100; revision-preparation and revision-attempt histories default/cap at10. The gateway-probe timeline alone declares descending order; other profiles declare ascending. ReadPageRequest checks exact limit type/range and cursor profile/collection/scope. Route adapters apply table defaults; the request itself requires a limit. ReadCollectionSpec has no constructor validation for arbitrary independently created specs; production lookups use the closed module table.

ReadPage.from_candidates accepts an exact tuple of at most limit+1 typed candidates and checks every cursor, including the hidden lookahead row. It exposes the first limit items and returns the last exposed cursor only when an extra row exists. It neither sorts nor verifies monotonicity, uniqueness, item-to-cursor identity or progress beyond the incoming cursor. Producers own correct keyset SQL and ordering: the selected session_page implementation filters workspace, seeks on created_at/session_id, orders on that pair and fetches limit+1. This is not a snapshot across requests or a bound on database work.

Direct ReadPage construction is refused. map preserves request, item order and the already-derived next cursor; mapper exceptions propagate unchanged, and mapping is not automatically pure or redacting. Frozen containers are shallow: generic item values can remain mutable. descriptor requires exact dict items and shallow-copies them, emitting workspace/kind/limit/items/next_cursor. Only revision-scoped descriptors get the1MiB ASCII-JSON encoded bound and fixed serialization error handling. That check is not universal nested schema validation or redaction; json.dumps uses its default nonfinite-number policy. Other collection descriptors have no aggregate byte cap here. Projection owners must supply bounded safe item content.
