PostgresUnitOfWork owns one caller-created connection and the application transaction around a group of store operations. Entering calls the factory and constructs [PostgresStoreBundle](../../../../../../control-plane-kit-operations/src/control_plane_kit_operations/postgres/stores.py) with that same connection. It does not install schema, authenticate a command, start a provider operation or choose retry/recovery policy. The factory must supply appropriate transactional behavior; the protocol names execute/commit/rollback/close but does not runtime-check autocommit, isolation level or connection health.

`commit()` requests commit; it does not physically commit yet. Stores remain available afterward, so a later application exception still causes rollback. On successful context exit with a request, __exit__ calls physical commit once; on an exception or an unrequested exit it rolls back. Physical commit failure, including BaseException, triggers a rollback attempt and re-raises, with close attempted in finally. Explicit rollback happens immediately and marks the unit finished; its later context exit only closes. There are no retries, savepoints, nested transaction support or cross-provider atomicity.

State guards reject store access before entry/after finish, lifecycle calls without an active unfinished connection, duplicate commit requests and nested entry while a connection remains attached. close clears the UoW's connection/store references before closing the connection. A previously closed instance can be entered again and resets its flags; the class is not permanently single-use and provides no synchronization for shared concurrent access. Retaining a store or connection reference bypasses the UoW property guard: ownership is a programming convention, not capability revocation. The bundle has no own commit/rollback methods, but exposes the underlying connection.

Failure boundaries matter. A factory or bundle-construction failure during __enter__ is not covered by its __exit__ cleanup. A rollback or close failure can mask an earlier application/commit exception; no secondary-error journal or universal primary-exception preservation exists. A database commit exception can represent uncertainty about what the database accepted, so an attempted rollback is not proof that no durable write committed. Closing early inside the active context is not a supported transaction-completion operation. These are source limits, not newly executed failures or permission to add recovery machinery.

The [owning tests](../../../tests/test_unit_of_work.py.md) distinguish fake lifecycle counters from real database visibility/rollback. The [session primitive tests](../../../tests/test_session_serialization_primitives.py.md) also use separate UoWs for lock and ordinal examples. Neither proves arbitrary caller transaction correctness or rollback of external effects. Lock ordering, idempotency, approval and domain mutations remain owned by the command services and stores sharing this connection; UoW only provides the commit boundary.
