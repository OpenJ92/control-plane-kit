`ApprovalCommandService` records requests for review and decisions, not execution. Its three commands are `RequestApproval`, `RequestGatewayKeyRotationApproval` and `DecideApproval`. Each fresh command writes a durable request or decision plus correlated ordered operation-action evidence in one unit of work. It does not admit execution, start a run, advance a graph, generate a key or move a rotation to another state. Actor IDs and scopes are supplied by the caller; credential authentication belongs outside this owner.

## Fresh authority and subjects

An ordinary request locks the session, requires it open and the action key unused, and loads a same-session plan without review blockers. Core [ApprovalPolicy](../../../../../control-plane-kit-core/src/control_plane_kit_core/policies.py) requires `PLAN_REQUEST` and derives maximum risk, destructive status and the decision scope from that persisted plan. This path does not recompile the plan or independently prove graph freshness, a nonempty plan or a PLANNED record status. Later [admission](../../../../../control-plane-kit-operations/src/control_plane_kit_operations/admission.py) owns its additional execution checks.

A rotation request requires a same-workspace durable rotation in REQUESTED and `DELEGATION_KEY_ROTATE`. It constructs the closed Core [rotation approval subject](../../../../../control-plane-kit-core/src/control_plane_kit_core/approval_subjects.py), then locks/rechecks the rotation and rejects an existing approval request for it. The request is HIGH risk, destructive and requires `DELEGATION_KEY_ROTATE_APPROVE`. Its subject identifies the review intent without embedding secret material. Requesting approval does not itself advance the rotation or establish provider/key-custody truth.

A fresh decision requires an open matching session, an unused action key and no existing decision for the request. Approval and rejection both follow the policy authorization path. Plan decisions use the recorded destructive flag; rotation decisions use their focused approval scope and destructive separation rule. Default policy requires distinct requester/decider actor strings for destructive work, but explicit `ALLOW_SELF` policy is supported; nondestructive self-approval is allowed. This is a policy decision over supplied principal IDs, not independent proof of credential identity. A decision records the scope required by the request and does not confer blanket authority over unrelated plans or rotation children.

## Receipt replay and transactions

The service first takes the session/action idempotency lock. Request replay looks up session/key; decision replay looks up request/key. Matching receipts return the stored fact and correlated action before fresh scope, open-session or target-state checks. Fingerprints include command kind, target coordinates, actor, comment and decision where applicable, but exclude actor scopes. Changed intent conflicts; missing or inconsistent action evidence fails. Do not describe this as fresh authorization or effect redispatch. The request result descriptor always says `pending`: it describes the request receipt, not a current approval projection after a later decision.

[PostgresActivityHistoryStore](../../../../../control-plane-kit-operations/src/control_plane_kit_operations/postgres/activity_history.py) owns persistence and scoped advisory locks. Session row locking serializes commands with session close/cancel and ordered action assignment; the rotation branch additionally locks the target rotation. [PostgresUnitOfWork](../../../../../control-plane-kit-operations/src/control_plane_kit_operations/postgres/unit_of_work.py) commits on successful context exit after the service requests commit, otherwise rolls back and closes. A late action-write failure must not leave a request or decision behind. Stores do not independently commit, and no provider call occurs in this transaction.

Commands and records accept an optional nonempty comment and retain it in durable storage; there is no comment size cap or universal secret scrub here. Command descriptors expose `comment_present`, and result/action projections omit comment text, but this does not make every internal object safe to publish. Store errors may retain chained causes. Keep public redaction and bounds at their actual interface owners rather than claiming a global sanitizer.
