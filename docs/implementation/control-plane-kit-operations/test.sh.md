This is the established Docker-backed Operations package gate, not a read-only diagnostic or live-provider acceptance wrapper. Before Docker commands it requires a present, clean architecture-testing checkout at the script's exact commit; its location is configurable. CI checks out that same coordinate and passes its path. Missing/wrong/dirty prerequisite is apparatus failure. Follow [TESTING.md](../../TESTING.md): stop and ask rather than substitute host Python/Postgres, install a host dependency or invent another harness. Reading this companion grants no invocation or cleanup authority.

The script runs the root [package integrity checker](../../../test_support/package_integrity.py) in a Python container over RO package/test-support mounts before creating the test network. The checker statically reports contract/test/mock/approved-skip counts and returns nonzero for findings; that output is not behavioral test success. The gate then creates one network and a named Postgres16-alpine container with disposable database credentials and a 2GiB noexec/nosuid tmpfs data directory. Its health loop checks up to sixty times with one-second sleeps, then one final inspection; this is not an overall suite or Docker-command deadline. Failure prints at most400 Postgres log lines, not a byte-bounded redacted public report.

The main Python container mounts same-checkout Core/Operations and governing architecture/docs/workflow inputs RO, copies package source into /tmp, installs Core then Operations and runs unittest discovery. Architecture-testing is available through its RO source mount/PYTHONPATH, not installed into host Python. The database URL selects the named disposable Postgres. Two later separate Python containers repeat temporary package installation for compileall and an outside-source import/version check; the final container also requires architecture-testing to be absent. Pip logs stay in ephemeral containers; no durable manifest or universal failure log retention is implemented here.

Python image, network and Postgres names have environment overrides. Python defaults to3.14-slim; Postgres uses16-alpine. These are tags, not immutable identity seals; Docker pulls and pip network resolution are not disabled. Integrity/compile/import use ordinary Docker networking, while behavior uses the created network. No Docker socket is mounted into the test containers. These isolation choices are not a security proof or provider credential admission.

cleanup force-removes the configured Postgres container with its volumes and removes the configured network, ignoring errors. It is installed as EXIT trap before integrity and also called before network creation. It does not inspect ownership/foreign attachments or prove absence, and can run after an integrity failure. Safe admission must therefore establish exclusive use of those names before an authorized invocation; do not infer ownership from this script's cleanup function. Foreground runners use --rm but are unnamed and are not separately selected by the cleanup trap. Cleanup failures can leave residue without overriding the primary result. This note documents the existing boundary, not an authorization to sweep, retry or repair it.

set -eu stops ordinary failed stages; the unittest branch preserves its docker/test exit after best-effort Postgres logs. Compile/import must also succeed for overall success. CI supplies a30-minute job bound externally; the shell itself has no equivalent global timeout. Full132-line gate read; selected actual integrity CLI/report and scanner entry context, CI checkout/job, Docker-only stop rules and [packaging metadata](pyproject.toml.md) checked. No script, test, build, install, Docker/database/provider operation or credential access was performed for these notes.
