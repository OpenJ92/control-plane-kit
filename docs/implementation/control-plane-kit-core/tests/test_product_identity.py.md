Nine tests cover ProductIdentity as the structural triple of namespace, name and positive contract revision. The first asserts each field, the slash-separated key and exact three-field descriptor. A second accepts a namespace named for an external application; that string is data, not a request to discover or import the application. Namespace admission does not establish a trusted publisher or reserve a name globally.

Eleven constructor cases reject uppercase namespace/name, non-ASCII text, a traversal-shaped name, a semicolon, whitespace, empty namespace/name, zero or negative revision, and Boolean revision. The actual [identity value and validators](../../../../control-plane-kit-core/src/control_plane_kit_core/products.py) accept lowercase ASCII alphanumeric runs separated by single dots or hyphens, cap each text part at 96 characters, and require an exact positive int revision. The test table does not check the length boundary, every separator arrangement or all wrong types; positive revisions have no upper bound in this constructor.

One codec round-trip checks both value equality and re-encoded descriptor equality. Four malformed descriptors exercise an extra key, missing name, string revision and Boolean revision. Source inspection supplies the exact-key and type contracts; these examples are not an exhaustive hostile-mapping or error-disclosure suite.

The ordering example checks namespace ordering and revision ordering within one name. The dataclass actually compares namespace, name and numeric revision in field order; the example does not separately isolate ordering between two names in one namespace or distinguish numeric revision ordering from lexicographic ordering of rendered keys. The duplicate test passes three identities to require_unique_product_identities and checks DuplicateProductIdentity with the repeated key. Another mixes one identity with an object and expects ProductIdentityError. The helper materializes inputs, validates members before sorting, then rejects duplicates. Neither test mutates a catalogue or instruments sorting; their names describe the intended boundary. Catalogue behavior is covered separately in [test_product_catalog.py](test_product_catalog.py.md).

The final test parses products.py for eight forbidden import roots and direct calls spelled `__import__(…)`. It is a finite syntactic check over that file, not transitive import analysis or proof that every possible effect mechanism is absent. Lexical identity restrictions and these AST checks do not authenticate products, sanitize all presentation contexts or authorize deployment.
