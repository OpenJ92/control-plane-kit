Four tests connect product declaration to graph serialization, structural diff and pure activity planning. Each helper call builds a fresh document/catalogue, instantiates the selected identity at role hello-blue, then compiles it under a DockerRuntime topology value. Image digest and contract revision are controlled inputs; the helper also returns the document digest. No registry, Docker service or durable execution session is involved.

The serialization example checks three metadata values after a graph-codec round-trip: product identity, product descriptor digest and digest-pinned image reference. It does not assert full graph equality in this method; the neighboring [instantiation tests](test_product_instantiation.py.md) cover that for their fixtures. Selected [product materialization](../../../../control-plane-kit-core/src/control_plane_kit_core/products.py) emits these metadata fields, and the graph compiler and codec preserve them as node data. They are declared provenance, not evidence that a provider ran those bytes.

Changing the image digest under the same product identity must change document digest. After validating each graph and diffing them, the test selects exactly one ModifiedChange for hello-blue's NODE_METADATA field, checks MetadataValue on both sides and verifies their respective document digests. The cardinality assertion applies to that filtered subset, not the entire diff. It then checks that the compiled plan contains some ReconcileNode and reports ready_for_execution. It does not assert the reconciliation target, complete activity count/order, health dependencies or risk classification.

Selected [diff code](../../../../control-plane-kit-core/src/control_plane_kit_core/topology/diff.py) compares node metadata as a whole field. The [planning compiler](../../../../control-plane-kit-core/src/control_plane_kit_core/planning/compiler.py) groups node field changes for reconciliation and adds health work; its policy is generic rather than an image-specific deploy path. In [ActivityPlan](../../../../control-plane-kit-core/src/control_plane_kit_core/planning/activity_plan.py), ready_for_execution means no ReviewChange operation remains. It does not establish approval, runtime authority, image availability, operational readiness or successful execution.

The revision example finds a ModifiedChange whose MetadataValue contains identity revision 1 before and revision 2 after, despite an unchanged role ID. Unlike the image case, it does not additionally filter the owner/field or assert uniqueness. The initial-deployment example diffs an empty graph against the product graph and checks for some StartNode plus ready_for_execution. It does not assert the exact start target, runtime-start activity or dependency structure. Selected compiler source handles owned node additions with normal start/health activities; these assertions stop before interpreting them.
