# Failed-run compensation program values

This owner represents a proposed compensation program as lineage, successful-effect evidence and ordered steps. It constructs and serializes pure values; it does not load a failed run, authenticate its evidence, choose an inverse, grant approval, persist admission or execute recovery. The only reason variant is POST_EFFECT_FAILURE. A valid value is an inspectable structural claim, not proof that compensation is safe or authorized.

Lineage pins workspace/request/run/plan, current and desired graph identities, a non-negative desired revision and an execution-intent fingerprint. Local identifiers are exact strings using 1–200 ASCII characters, alphanumeric first and then alphanumerics plus period, underscore, colon or hyphen. RunId and EffectAttemptIdentity adopt the [recovery identity contract](recovery.py.md). Fingerprints are exact strings of 64 lowercase hexadecimal characters; this owner does not verify their preimages. Revisions and completion ordinals reject booleans and integer subclasses, but have no database-width ceiling here.

Evidence requires a non-empty exact tuple of SuccessfulEffectEvidence values, all from the lineage run. Completion ordinals must be unique and descending; attempt identities must also be unique. The completion-event identifier is syntactically checked but not independently required to be unique or correlated to a stored event. Each step has a positive exact-integer position, one source effect, an encodable activity operation and an exact BASE_GRAPH or DESIRED_GRAPH material-source enum. Programs require a non-empty exact tuple of steps, positions exactly 1 through N, and source effects exactly equal to the evidence tuple in order.

These are laws over supplied values. They do not prove that every successful effect in a run has been supplied, that an operation targets its source activity, or that operation/material source form the correct inverse. Step construction calls the single-operation encoder, not the stronger planned-activity validator: the encoder recognizes operation and target variants independently. Do not assume it establishes every operation/target pairing or restricts steps to safe inverse operations.

The actual [Operations admission consumer](../../../../../../control-plane-kit-operations/src/control_plane_kit_operations/failed_run_compensation.py) separately compares stored request/run/workspace/plan lineage and terminal failure evidence, rejects unresolved attempts or incomplete succeeded-effect evidence, then reads each admitted activity's compensation. It selects Compensate entries, omits NoCompensationRequired entries and rejects NonCompensatable entries. Consequently this program's successful_effects describes the selected compensatable subset. Operations owns that selection and its transaction; this note's selected consumer read is not a complete authorization, replay or execution audit.

The schema-tagged version-one descriptor uses lists for evidence and steps, exact dict/key sets for this owner's envelopes, and nested constructors on decode. Fingerprinting hashes compact, sorted-key, ASCII JSON of the reconstructed descriptor with SHA-256, including program_id. It is a content commitment to these values, not a signature, independent evidence check or semantic identity that excludes the program ID.

Closure has two material limits. Schema/version are compared by equality rather than exact primitive type, so values equal to integer 1 are not rejected solely for their type. Nested operations use the [standalone activity codec](../planning/codec.py.md), which can ignore extra operation/target fields; this owner adds no re-encoding equality check. Do not describe all nested wire data as losslessly closed. Fixed local error messages do not establish general redaction: wrapped ValueError/TypeError causes are retained, and operation decoding may expose supplied variant text. There is no complete descriptor byte/depth or tuple-length budget here.
